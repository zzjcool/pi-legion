# 并行派发子任务策略（herdr 多 pi 进程）

当并行/子 agent 工作可用时，通过 subagent 工具启动多个独立 pi 进程完成，主 pane 只做汇总决策。以下场景必须主动派发，不要等用户提醒：

## 侦察必须并行（最重要的提速规则）
- **主会话禁止自己串行读代码探索**。凡是要理解现状——诊断 bug、体验问题定位、
  「这个流程是怎么走的」、改动前摸底——都是侦察工作，一律派 scout，主会话不自己干。
- **预估要读 3 处以上代码才能回答的，拆成多个 scout 并行**（`subagent({ tasks: [...] })`）。
  按链路/模块切分侦察面：如「前端 UI 流程」「后端执行链路」「数据/存储流」「相关测试与冻结文案」，
  每个 scout 一个独立任务，各自带明确的产出问题清单。
- 主会话在 scout 跑的时候只做轻量定位（`ls`、一两条 `rg`）或干脆等待，不要跟 scout 抢活。
- **任务进场先做读文件预算**：凡任务是「确认 review findings / 验证 bug 报告 /
  「帮我确认一下 X」」，逐条评估需要读几处代码才能回答——每条 ≥3 处即拆 scout 并行，
  只有全部条目 ≤2 处才允许主会话自查。侦察请求的确认属于侦察，不属于"简单问题"。
- 串行读 100 次 bash 是最差的形态：又慢又占满主会话上下文。并行 scout 收割事实清单后，
  主会话直接基于事实做裁决/方案。
- 反例（禁止）：thinking 里出现 "Let me explore the repo" 然后自己 rg/sed 一路读下去。

## 必须并行派发（在 subagents tab 下拆多个 pane，每 pane 一个 pi）
- **跨多目录/多模块的改动**：每个互不依赖的模块一个 pi worker，并行推进，主 pane 只做汇总。例：同时改后端+前端时，开两个 worker pi。
- **实现完成后的对抗式 review**：并行开多个 fresh-context `worker`，任务卡里写清各自的 review 视角（正确性/回归、测试覆盖、简洁性，并要求「只审不改」），再由主 pane 综合修复。**本包没有 `reviewer` 角色**——`BUILTIN_AGENT_NAMES` 只有 `scout` / `worker` / `centurion`（reviewer/planner/designer/prototype/advisor 在 #301 被删除）。
- **多个互不依赖的独立任务（测试/回归/调研）**：直接并行，不要串行排队。

## 必须派发（单个也派）
- **不确定方案时**：先开一个 pi 做第二意见，拿到建议再动手。
- **做方案的那个任务的产出是计划，不是基线实测**：任务卡里显式禁止跑集成/全量测试（至多 typecheck 或读 CI 结果），需要基线验证的是 worker 的 verify 门禁职责。违反此条是过度侦察，直接浪费 20 分钟级别的时间。**本包没有 `planner` 角色**：方案任务派给 `scout`（只读侦察、在回答里给方案）或 `worker`（需要落盘成文时）。
- **大改动前**：先侦察摸清代码（多路 scout 并行，见上）→ 出计划 → 再开 worker pi 实现。
- **需要查外部资料/文档时**：先派 `scout` 做侦察/第二意见（只读、不带历史），拿不准再自己查，不要自己瞎猜。**本包没有 `researcher` 角色**——可派发角色只有 `scout` / `worker` / `centurion`。
- **用户报告 bug / 体验问题要定位原因时**：这是典型的侦察场景，直接派 scout 并行摸事实，
  不要主会话自己逐文件读。

## 交付流水线：review 是合并门禁，merge 权在主 agent
- worker 交活（自报 verdict + 分支；有 remote 时才附 MR）→ 主 agent 派一个 fresh-context `worker` 做合并门槛审查（任务卡写明「只审不改」、结论以 `ok: true/false` 开头；本包没有 `reviewer` 角色）。分支与 MR 只在主 agent 显式授权时才存在，见「派发纪律」的越权条目。
- **审查任务卡里必须附上冻结契约的关键决策**（出方案那一方的 D 编号决策、刻意删除/不改的项），否则审查方会把「刻意为之」误判为「缺失功能」，引发不必要的返工循环（契约矛盾型 major）。
- 审查方报 critical/major findings → steer 原 worker 修复 → 复审；minor 可接受后合入。修复范围应由主 agent 按契约裁决后裁剪，全盘照单转给 worker 是浪费。
- **交付物是分支**：`git log` 能看到、`git diff` 能审就够；MR 只是有 remote 时的便利，不是门槛。
- **合并由主 agent 统一做，worker 永不自己 merge**。并行多个分支时按出方案一方标注的集成顺序合（共享文件的改动必须序列化），冲突时主 agent 裁决。

## 不要派发（保持单 agent，避免无谓开销）
- 改单个文件的单个函数、跑测试、看日志、回答简单问题。
- 用户明确说"直接改""别绕"时。
- 任务本身只值一次工具调用的微小操作。

## 派发纪律
- **worker 不得自作主张 `git commit` / `git push` / 建分支 / 开 PR**：交活只交 verdict + 工作区改动（或任务卡里显式写明的那个分支）。`commit`、`push`、建分支、开 PR 各算一次越权——verify 门禁只跑命令，不替父会话落盘历史，更不替它对外发声。需要分支/MR 时由主 agent 在任务卡里**显式授权并写明分支名**（例：`分支：feat/x`），worker 自己开 PR 属于越权。若 worker 已经建了分支/PR：由主 agent 决定保留还是关闭，worker 不得自行 `push` 到受保护分支（`main`/`master`），也不得自己 merge。
- review/侦察类用全新会话（不 --session 继承），避免主会话历史污染判断。
- 写操作类 worker 同一 worktree 只留一个 writer，避免冲突。
- worker 只接收具体任务，不要让 worker 再自己开 worker/写操作子 agent；
  卡住时回 verdict 上报、由父会话裁决的机制见「失败止损」。
- 长任务在 worker pane 后台跑，主 pane 收割状态，别空等。
- **等待要事件驱动，不要轮询/干等**：派工后优先用 `subagent({ action: "wait", all: true })`（或带具体 `name`）等完成事件，或在下一个自然时机主动收割；不要静置 20+ 分钟后等用户来问「为什么还在跑」。用户发问「还在跑吗」本身说明等待期没有可观察的进度信号。`wait` **必须**带 `name` 或 `all: true`，二者互斥。

## 契约先行（多 worker 并行改同一仓库）
- 跨 worker 的改动，先出**冻结契约文档**落库（接口形状、wire 字段、
  文件归属、验收清单）再派工；各 worker 在独立 worktree 互相看不见
  对方改动，契约就是唯一接口。
- 每个 worker 任务里显式列出**文件所有权清单**（你的文件，禁止越界）；
  共享文件序列化给一个 worker，不并发。
- worker 报「契约矛盾」是**正确拒绝**：修订契约（落库、注明修订原因）
  后重派，不让 worker 自行解释矛盾。
- 计划文档若在另一分支新增，worker 本地可能拉不到——任务里写明
  「看不到就向父会话要内容，禁止自己新建同名文件」。
- 合并阶段主 agent 亲自补三类缝隙：任务分配没写到的协调点、跨分支
  集成测试、契约修订后的收尾。

## 卡死检测：长时间 working 不等于在干活
- worker 的探针/诊断脚本必须 `timeout 60 <cmd>` 包裹、socket 必须 `settimeout`，
  否则裸 recv/死循环会永久挂起 worker（表现为 working 但零进展）。
- 派发后应在下一个自然时机（或用户提醒时）检查一次 worker 是否真的在推进。
